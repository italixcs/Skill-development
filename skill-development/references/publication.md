# Documentation and publication

## Separate useful preparation from publishing

Prepare the candidate and reviewable evidence within authorized scope. Commit, push, create a release, change visibility, publish a report, or contact anyone only when explicitly authorized for that action and destination. Do not treat "prepare for release" as publication permission.

If asked only to assess supplied evidence, answer that readiness question, the material blockers, and the next relevant checks. Keep unrelated release steps out of the response. Clearly distinguish synthetic test entries, historical reports, and findings established about the real current candidate; investigate genuine findings without presenting a fixture as a real vulnerability.

Private skills need clear usage and maintenance information appropriate to their user. Omit public marketing requirements. Public skills need the checks below.

## Use Repo Cleaner conditionally

Invoke an available Repo Cleaner when the repository needs installation, examples, evidence presentation, navigation, or metadata work. Supply the verified purpose, audience, artifact paths, real outputs, supported installation routes, compatibility evidence, and scoped authorization.

Read its instructions and preserve application behavior, license, and visibility. Skip decorative assets unless they improve comprehension or were requested. If Repo Cleaner is unavailable, prepare essential factual docs with native file tools; do not claim the integration ran.

A concise README should let a new user identify the purpose, prerequisites, complete installable folder, first useful invocation, and important limitations. Keep actual instructions as text. Use real outputs for showcases; label concepts and local reconstructions.

## Public readiness

Before claiming readiness, verify:
1. The installable package contains every required resource and passes applicable structural checks.
2. Necessary scripts/commands and the shortest installation path are checked within available permissions. State runtime-tested, documentation-checked, or manual-only separately.
3. Evaluation supports the actual usefulness claims; retained failures and isolation limits are visible. No statistical or universal claims from a small diagnostic.
4. A completed SkillSpector scan covers the declared distribution scope; serious findings are resolved or demonstrably false positive, with evidence. Other unresolved required checks remain blockers.
5. Licensing, redistributed resources, upstream attribution, and dependency terms have been reviewed. Do not assume one repository license licenses all imported material.
6. Public files contain no secrets, private task inputs, unsanitized traces, A/B mapping, or temporary signed URLs.
7. README, examples, security/evaluation summaries, and release notes match the exact candidate. Link evidence rather than duplicating full reports.
8. The target host/version evidence and known limitations are accurate; optional tools are clearly optional.
9. The actual remote actions have explicit authorization. Readiness itself grants none.

An explicitly manual-only or documentation-checked host route can be documented honestly without claiming native runtime support. Untested additional hosts do not prevent completion of the skill or release under a narrower, verified claim. Do not require output-quality superiority to publish a workflow whose stated purpose is process consistency.

If the package changes, identify which checks and public claims are affected and repeat those only. Final packaging must preserve the reviewed file contents; verify identity again before an authorized release.

Use existing release history or release notes; avoid extra files solely to satisfy a template. Record concrete behavior changes, prerequisites, and limitations.

## Handoff

Separate prepared local artifacts, applied remote changes, skipped optional work, and blocked required work. For authorized remote mutations, verify the resulting destination/revision/settings. A local metadata file does not apply GitHub settings.

If asked to publish despite unresolved blockers, describe them accurately and retain the blocked readiness status. Do not disguise risk acceptance as a completed check or weaken host safety requirements.
